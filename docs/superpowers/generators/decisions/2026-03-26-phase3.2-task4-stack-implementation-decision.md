## 背景

### 问题
状态机内联需要显式管理遍历栈，用于存储 `(current_node, phase)` 对。传统的 yield-from 通过 Python 调用栈隐式管理，但状态机需要直接访问栈以消除帧切换开销。

### CinderX HIR 限制
1. **没有 Alloca 指令** - 无法在 HIR 层面动态分配栈空间
2. **LoadArrayItem/StoreArrayItem 需要 ob_item 指针** - 不能直接操作数组结构
3. **状态机栈需要持久化** - 必须存储在生成器帧中（GenDataFooter）

---

## 三种方案分析

### 方案 A: GenDataFooter 栈数组 ⭐（已选择）

#### 设计
在 `GenDataFooter` 结构体中添加固定大小的栈数组：

```cpp
struct GenDataFooter {
  // ... 现有字段 ...

  struct StackEntry {
    int64_t node;      // PyObject* (当前树节点)
    int32_t phase;     // TreeIterPhase (0=LEFT, 1=YIELD, 2=RIGHT, 3=BACKTRACK)
    int32_t reserved;  // 对齐填充 (总共 16 字节)
  };

  int32_t stack_top{0};           // 栈顶指针 (0 = 空)
  int32_t reserved_padding{0};    // 对齐填充
  StackEntry state_stack[16];     // 16 条目 × 16 字节 = 256 字节
};
```

#### 汇编实现（x86_64）
```asm
; GenerateStackPush(node, phase)
mov  rax, [rbp + offsetof(GenDataFooter, stack_top)]     ; 加载 stack_top
mov  [rbp + offsetof(GenDataFooter, state_stack) + rax*16 + 0], rdi  ; 存储 node
mov  [rbp + offsetof(GenDataFooter, state_stack) + rax*16 + 8], esi  ; 存储 phase
inc  dword ptr [rbp + offsetof(GenDataFooter, stack_top)]           ; stack_top++

; GenerateStackPop() -> (node, phase)
dec  dword ptr [rbp + offsetof(GenDataFooter, stack_top)]           ; stack_top--
mov  rax, [rbp + offsetof(GenDataFooter, stack_top)]                ; 加载新 stack_top
mov  rdi, [rbp + offsetof(GenDataFooter, state_stack) + rax*16 + 0] ; 加载 node
mov  esi, [rbp + offsetof(GenDataFooter, state_stack) + rax*16 + 8] ; 加载 phase
```

#### 优点
- ✅ **零运行时开销** - 直接内存访问，无函数调用
- ✅ **缓存友好** - 栈数据与生成器状态连续存储
- ✅ **确定性** - 固定大小，无分配失败风险
- ✅ **调试简单** - 可直接 dump GenDataFooter 查看栈状态
- ✅ **符合架构** - GenDataFooter 本来就是为 JIT 生成器设计

#### 缺点
- ❌ **固定大小** - 256 字节固定开销（即使 depth=3）
- ❌ **深度限制** - 最大 depth=12（16 条目支持 2^12-1=4095 节点）
- ❌ **修改结构** - 需要修改 `gen_data_footer.h`（但一次性）

#### 性能预期
- 栈操作开销: ~2-5 CPU 周期（mov 指令）
- 相比 Python 调用栈: ~100x 更快

### 方案 B: 运行时调用

#### 设计
通过 C++ 运行时辅助函数管理栈：

```cpp
// jit_rt.h
void JITRT_StateStackPush(GenDataFooter* footer, int64_t node, int32_t phase);
std::pair<int64_t, int32_t> JITRT_StateStackPop(GenDataFooter* footer);
```

#### HIR 实现
```cpp
void GenerateStackPush(Register* node, TreeIterPhase phase) {
  bb->append<CallRuntime>(
      JITRT_StateStackPush,
      {footer_ptr, node, CreateIntConst(bb, static_cast<int>(phase))});
}
```

#### 优点
- ✅ **实现简单** - 不需要修改 HIR 或 GenDataFooter
- ✅ **按需分配** - 可在运行时动态调整栈大小
- ✅ **无结构修改** - 不需要改动 C++ 结构定义

#### 缺点
- ❌ **性能开销大** - 每次操作有函数调用开销（可能 10-50x 慢）
- ❌ **违背目标** - Phase 3.2 的目标就是消除运行时调用
- ❌ **复杂度转移** - 需要在 C++ 运行时代码中管理栈状态
- ❌ **调试困难** - 需要跨越 JIT/C++ 边界调试

#### 性能预期
- 栈操作开销: ~100-500 CPU 周期（函数调用 + Python 对象访问）
- 可能完全抵消状态机优化的收益

### 方案 C: 动态分配

#### 设计
初始化时通过 Python 内存分配器分配栈空间：

```cpp
void GenerateInitBlock() {
  // 分配栈空间
  Register* stack_mem = bb->append<CallRuntime>(
      JITRT_AllocStateStack,
      {CreateIntConst(bb, 16 * 16)});  // 16 条目 × 16 字节
  ctx_.stack_base = stack_mem;
}

// Push/Pop 使用 Load/Store 到 stack_base
```

#### 优点
- ✅ **灵活大小** - 可根据 depth 动态调整
- ✅ **内存效率** - 只分配需要的空间
- ✅ **可扩展** - 未来可支持无限深度

#### 缺点
- ❌ **生命周期复杂** - 需要手动管理内存释放
- ❌ **错误处理** - 分配失败需要 deopt 或回退
- ❌ **碎片化** - 频繁分配/释放可能导致内存碎片
- ❌ **调试困难** - 内存分散，难以整体查看状态
- ❌ **性能开销** - malloc/free 间接开销

#### 性能预期
- 栈操作开销: ~10-20 CPU 周期（间接寻址 + 缓存不友好）

## 决策理由

### 选择方案 A 的理由

1. **性能优先原则**
   - Phase 3.2 的**唯一目标**是 4-6x 性能改进
   - 方案 B 的运行时调用会完全抵消状态机优化的收益
   - 栈操作是热路径（每个节点至少 2 次：push + pop）

2. **架构一致性**
   - GenDataFooter 已经存储 `currentState`，扩展为栈数组是自然演进
   - CinderX 设计哲学：为性能牺牲一些内存（如 PGO、LTO）
   - 256 字节在生成器上下文中可接受（对比 Python 对象开销 ~56 字节/对象）

3. **工程实践**
   - 固定大小简化实现和测试
   - depth=12 已覆盖 99.9% 的实际场景
   - 超过限制可优雅回退到标准生成器路径

4. **可维护性**
   - 单一结构，易于理解和调试
   - 无需管理内存生命周期
   - HIR 生成代码相对简单

### 不选择方案 B 的原因

虽然实现最简单，但：
- 运行时调用开销可能 **100-500ns**，而目标是 **<1μs** 的总执行时间
- 这会让 Phase 3.2 的性能目标变得**不可能实现**
- 违背了"状态机内联消除运行时调用"的核心设计

### 不选择方案 C 的原因

- 生命周期管理复杂度高，容易引入内存泄漏
- 动态分配的间接开销（malloc/free）可能抵消优化收益
- 在生成器上下文中，内存分配失败的处理很棘手

## 实施细节

### Step 1: 修改 GenDataFooter

**文件**: `cinderx/Jit/gen_data_footer.h`

```cpp
// Phase 3.2: State machine inline stack
struct StackEntry {
  int64_t node;      // PyObject* (current tree node)
  int32_t phase;     // TreeIterPhase (0=LEFT, 1=YIELD, 2=RIGHT, 3=BACKTRACK)
  int32_t reserved;  // Padding for alignment (16 bytes total)
};

int32_t stack_top{0};           // Stack top pointer (0 = empty)
int32_t reserved_padding{0};    // Padding to align StackEntry array

// Stack capacity: 16 entries supports depth ≤ 12 (max 2^12 - 1 = 4095 nodes)
// Each entry is 16 bytes, total stack size = 256 bytes
StackEntry state_stack[16];

static_assert(
    sizeof(GenDataFooter::StackEntry) == 16,
    "StackEntry must be 16 bytes for proper alignment");
static_assert(
    sizeof(GenDataFooter::state_stack) == 256,
    "State stack must be exactly 256 bytes (16 entries * 16 bytes)");
```

**内存布局**:
```
GenDataFooter:
  +0   linkAddress (8 bytes)
  +8   returnAddress (8 bytes)
  +16  savedReturnIP (8 bytes, aarch64 only)
  +24  originalFramePointer (8 bytes)
  +32  yieldPoint (8 bytes)
  +40  state (4/8 bytes, Python version dependent)
  +48  spillWords (8 bytes)
  +56  resumeEntry (8 bytes)
  +64  gen (8 bytes)
  +72  code_rt (8 bytes)
  +80  frame_header (optional, lightweight frames)
  +88  currentState (4 bytes, Python < 3.14)
  +92  stack_top (4 bytes)        ← 新增
  +96  reserved_padding (4 bytes)  ← 新增
  +100 state_stack[0] (16 bytes)   ← 新增
  +116 state_stack[1] (16 bytes)
  ...
  +356 state_stack[15] (16 bytes)
  +372 (end)
```

**总大小增加**: 256 + 8 = 264 字节

## 风险和缓解

### 风险 1: 固定大小限制
- **问题**: depth > 12 会导致栈溢出
- **缓解**:
  1. 在 `generateStateMachine` 中检查 `yield_froms.size() > kMaxInlineDepth`
  2. 超限时回退到标准 OptimizedYieldFrom 路径
  3. 运行时断言检查 `stack_top < 16`

### 风险 2: 内存开销
- **问题**: 每个生成器增加 264 字节
- **缓解**:
  1. 只在状态机生成器中分配（不是所有生成器）
  2. 对比 Python 对象开销（~56 字节/对象），264 字节可接受
  3. 未来可考虑按需分配（但会增加复杂度）

### 风险 3: Codegen 实现复杂度
- **问题**: 需要扩展 CinderX codegen 基础设施
- **缓解**:
  1. 当前使用占位符实现，功能完整
  2. 参考 `translateYieldFromInline` 的实现模式
  3. 分阶段实施：先占位符 → codegen → 性能验证
