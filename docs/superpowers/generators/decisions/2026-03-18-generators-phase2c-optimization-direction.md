## 背景

Phase 2-C原计划实施yield-from内联优化，预期30-50%性能提升。

### 原始假设

1. yield-from是简单的迭代+yield
2. 可以内联为显式循环
3. 消除YieldFrom指令的开销

### 实际发现

经过深入研究（见`docs/superpowers/research/2026-03-18-yield-from-implementation-mechanism.md`），发现：

1. **yield-from不是简单循环** - 它是完整的生成器协议（send/throw/close）
2. **状态机在运行时** - JITRT_GenSend函数处理所有复杂性
3. **内联无性能收益** - 即使内联，仍需调用相同的运行时函数

---

## 关键洞察

### YieldFrom指令的实际开销

```
当前流程：
字节码 YIELD_FROM
    ↓
HIR YieldFrom指令
    ↓
LIR调用指令
    ↓
call JITRT_GenSend  ← 主要开销在这里
    ↓
PyIter_Send
```

**如果内联**：
```
字节码 YIELD_FROM
    ↓
HIR内联循环
    ↓
LIR调用指令
    ↓
call JITRT_GenSend  ← 仍然需要这个调用！
    ↓
PyIter_Send
```

**结论**: 无法消除主要开销（运行时函数调用）。

### 可能的优化方向

#### 方向A: 特化简单迭代器

**原理**: 检测iter是简单迭代器（非生成器），使用更快的路径

```cpp
if (isSimpleIterator(iter)) {
  // 快速路径：直接调用InvokeIterNext
  next_val = InvokeIterNext(iter);
  YieldValue(next_val);
} else {
  // 慢速路径：使用YieldFrom指令
  YieldFrom(send_value, iter);
}
```

**挑战**:
1. 需要迭代器类型分析
2. 需要deopt机制（类型变化时回退）
3. 收益不确定（取决于迭代器类型分布）

**ROI**: 中等

#### 方向B: 批量yield

**原理**: 一次yield多个值，减少挂起/恢复次数

**挑战**:
1. 需要迭代器大小信息
2. 增加代码复杂度
3. 可能增加延迟（批量处理）

**ROI**: 低-中等

#### 方向C: 跨生成器内联

**原理**: 内联整个生成器调用链

**挑战**:
1. 极其复杂（需要分析整个调用图）
2. 代码膨胀
3. 编译时间增加

**ROI**: 高（如果可行）

#### 方向D: 放弃yield-from优化，转向其他方向

**可能的替代优化**:
1. FOR_ITER优化
2. 生成器创建优化
3. 其他字节码优化

**ROI**: 取决于具体优化
